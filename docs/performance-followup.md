# متابعة ملاحظات PageSpeed في الصور

> جولة تسريع لاحقة (فهرس الصندوق اليومي، مفاتيح التواريخ النصية، تصغير HTML): [performance-speed-2026-10-23.md](./performance-speed-2026-10-23.md).

الفرع: `arena/6f87d0ab-omega01` — 22 أكتوبر 2026.

## التشخيص والإصلاح

### 1. بيانات Firebase المكررة

الكود السابق كان يسجل مستمعي `onValue` لكل الأقسام، ثم يشغّل طلبات REST للأقسام نفسها بعد انتظار إنشاء SDK. ظهور `v2/customers.json` و`v2/products.json` إلى جانب `lp?...` في الصور يتوافق مع هذا المسار المزدوج.

- أصبح بدء التشغيل والتنقل يشتركان في أول snapshot لكل قسم عبر `createRealtimeSections`؛ لا طلب REST موازٍ لمجرد أن اتصال Firebase بطيء.
- REST يُستخدم فقط إذا تعذّر تهيئة SDK، مع الاحتفاظ بقراءة المسارات القديمة عندما يكون مسار v2 غائبًا فعلًا.
- أخطاء الشبكة/الصلاحيات لا تتحول إلى بيانات فارغة ناجحة، ولا تؤدي إلى طلب legacy إضافي. يمكن إعادة المحاولة.
- طلب legacy البطيء لا يستطيع الكتابة فوق snapshot أحدث.
- تحميل تاريخ المبيعات ينتظر وصول نافذة المبيعات الأولى، ولا يعيد طلبها بالتزامن. يترك وقتًا للواجهة بين صفحات التاريخ.
- قراءة إعداد إخفاء الأرصدة تقتصر على `appState/hideFinances` بدل تنزيل عقدة `appState` بأكملها.
- الحفاظ على إحصاءات `allTime` التي كان يوفرها مسار REST السابق، والتحقق من استمرار تحميل تاريخ المبيعات حتى عند فشل قسم آخر.
- إعدادات Firebase وSDK يُحمّلان بالتوازي، مع انتظار الإعدادات حتى عند فشل SDK كي يستخدم مسار REST قاعدة البيانات الصحيحة.

**لم تُختصر سجلات مالية أو أعداد المشتركين لتجميل القياس.** ما تزال الأقسام اللازمة لحسابات اللوحة تُحمّل كاملة، مع نافذة المبيعات والتحميل التاريخي كما في التصميم القائم.

### 2. JavaScript الأولي والتصغير

- فصل عرض التقرير الشامل وتصديره إلى `src/full-report.js`، وتحميله عند الطلب.
- فصل واجهة سجل العمليات إلى `src/activity-log-view.js`. تسجيل العمليات نفسه يبقى فوريًا؛ التأجيل يخص العرض فقط.
- حذف بيع من اللوحة لا يحمّل التقرير غير المفتوح.
- تطبيق Terser على حزمة Firebase فقط، مع إخراج إشعارات تراخيصها إلى `assets/firebase.LICENSE.txt` بدل فقدانها.
- تقليل تحديثات النصوص المتطابقة في `setElemText`.

### 3. الخطوط وتحرك الصفحة والتخزين

إصلاحات الفرع السابق موروثة هنا: إزالة Base64 للخطوط، تحميل ملفات الخطوط المحلية القابلة للكاش، وتجهيز CSS كاملًا قبل أول رسم. الصور كانت تُظهر بلوك الخطوط القديم؛ يلزم نشر النسخة الجديدة وإعادة PageSpeed على الرابط المنشور.

لم نضع ردود `lp?...` أو بيانات الأرصدة في كاش طويل. هذه ردود اتصال Firebase الحي وليست ملفات ثابتة؛ تطبيق نصيحة TTL عليها بشكل أعمى قد يعرض بيانات قديمة. الحل هنا إزالة النقل المكرر، لا تجميد بيانات المعاملات.

## التحقق

- `npm test`: **84 اختبارًا ناجحًا**.
- `npm run test:ui` مع jsdom: **6 اختبارات بيع وتسعير ناجحة**. يظهر تحذير التصدير العام الموجود في بيئة jsdom، لكن الاختبارات تنجح؛ اختبارات المتصفح لا تسجل أخطاء JavaScript.
- `npm run lint` وفحص syntax للملفات الجديدة: ناجح.
- `npm run build`: ناجح، مع بقاء تحذير حجم JavaScript الرئيسي وقارئ الباركود.
- `tests/startup-browser.check.mjs`: بناء إنتاج مع SDK تجريبي معزول، يحتوي 500 مشترك. لا يتصل ببيانات المستخدم أو يكتب إليها.
  - بعرض 412 و1440 بكسل: تحميل واحد للمشتركين، وعدم تنزيل نسختهم بـREST أو طلب نافذة المبيعات مرتين.
  - استمرار وصول تحديث المخزون الحي.
  - التقرير وسجل العمليات لا يُطلبان عند بداية الصفحة، ويعملان عند فتحهما.
  - تأخير البيانات 1.5 ثانية: CLS للهاتف **0** وللكمبيوتر حوالي **0.0011**.
  - عند فشل SDK: يستخدم REST إعدادات القاعدة المخصصة؛ رفض 403 لا يُسجل كنجاح، وتنجح إعادة المحاولة.

تشغيل اختبار المتصفح اختياري، مع Chromium/Chrome مثبت:

```sh
npm install --prefix .cache/browser-tools --no-audit --no-fund puppeteer-core
BROWSER_TOOLS_DIR=.cache/browser-tools CHROME_PATH=/path/to/chromium \
  node tests/startup-browser.check.mjs
```

## قياس Lighthouse وحدوده

ثلاث جولات على **نسخة الإنتاج المحلية الحقيقية، وليس بناء SDK التجريبي**، بإعداد الهاتف الافتراضي: **96، 96، 95**. قيمة CLS كانت **0** في الثلاث، واختبار JavaScript غير المصغر اجتاز الفحص. تفاصيل الأرقام محفوظة في `performance-followup-results.json`، والتقرير الكامل المحلي في `reports/lighthouse-followup.html` (غير متتبع في Git).

- Firebase الحقيقي غير قابل للوصول من بيئة القياس؛ لذلك **لم نقس حجم نقل بيانات المستخدم بعد الإصلاح**، ولا نزعم أن نقل Firebase البالغ نحو 3.6 MiB في الصور اختفى بالكامل. اختبارات التكامل تثبت إزالة مسار النقل المكرر، لا الحجم النهائي لقاعدة البيانات الحقيقية.
- بقي تحذير JavaScript غير المستخدم عند البداية. الفصل الحالي يخفض الحزمة ولا يلغي كل الوظائف غير المستخدمة على أول شاشة؛ إزالة باقي التحذير تحتاج فصل مزيد من الأقسام مع اختبارات وظائفها.
- قد تبقى بيانات المشتركين/صورهم كبيرة حتى بعد منع التكرار. تخفيفها أكثر يتطلب فصل الصور عن سجلات البيانات أو إعادة تصميم استعلامات اللوحة مع إحصاءات موثوقة؛ لم نغيّر مخطط قاعدة البيانات أو الأرصدة تلقائيًا.
- درجة 95–96 المحلية ليست بديلًا لنتيجة PageSpeed للرابط المنشور مع بيانات Firebase الحقيقية. يلزم إعادة الفحص بعد النشر؛ لم يتم النشر أو الدمج ضمن هذا التعديل.
