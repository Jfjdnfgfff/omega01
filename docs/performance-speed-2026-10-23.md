# جولة تسريع شاملة — 23 أكتوبر 2026

الفرع: `arena/03f4f5d7-omega01`. الهدف: تقليل زمن العرض والحسابات المتكررة مع
نمو البيانات، وتقليل حجم HTML الأولي — دون أي تغيير في الأرقام أو السلوك المرئي.

## التشخيص

قياس الكود أظهر ثلاثة اختناقات حقيقية أثناء التشغيل (لا تظهر في Lighthouse
لأنها تعتمد على حجم بيانات المستخدم):

1. **شاشة الصندوق**: `calculateAllCaisseShortages` كانت تستدعي
   `calculateCaisseDetails` مرة لكل يوم إقفال، وكل استدعاء يعيد بناء دفتر
   الحركات بمسح كل الأقسام المالية — أي O(أيام الإقفال × كل السجلات) عند كل
   عرض. يضاف إليها استدعاء `calculateCaisseDetails` لكل صف في جدول تاريخ
   الإقفالات، وداخلها مسح كامل لسجلات الصندوق (`creditPaymentsOnDate` + بحث
   الإغلاق) في كل مرة.
2. **لوحة القيادة** (`performFullRender`): لكل بيعة/مشترك/حصة كانت تُبنى
   كائنات `Date` وتُستدعى `toDateString()` (بطيئة خصوصاً) مرتين عبر حلقتين
   منفصلتين على المبيعات، وتُمسح المصاريف وخلاصات العمال مرتين
   (reduce + filter + reduce)، وتُعاد كتابة قوائم الباقات والغيابات وقائمة
   اختيار الباقة في DOM عند كل دورة عرض حتى دون تغيّر البيانات.
3. **فرز القوائم**: مقارنات الفرز كانت تبني `new Date` عند كل مقارنة
   O(n·log n) بدل مرة لكل سجل O(n) — في قائمة المبيعات والمصاريف (عرضان)
   ومعاملات العمال وتاريخ الصندوق.

وعلى مستوى الإقلاع: `index.html` الخام ‏375K محرف، نحو 24% منها مسافات إزاحة
وتعليقات، تُنقل وتُفسَّر عند كل تحميل بارد رغم أنها لا تعرض شيئاً.

## التعديلات

### 1. فهرس صندوق يومي بمسح واحد (`src/caisse-transactions.js`، `src/main.js`)

- نواة مشتركة `collectCaisseMovementsByDate` تجمع الحركات في دلاء يومية بمسح
  واحد لكل الأقسام؛ `buildCaisseMovements` (نفس التوقيع والنتائج حرفياً) صارت
  حالة خاصة ليوم واحد، و`indexCaisseMovementsByDate` يعيد Map لكل الأيام دفعة
  واحدة. تسويات اشتراكات الكريدي تُجمَّع مسبقاً حسب المشترك بدل ترشيح كل
  السجلات لكل مشترك.
- في `main.js`: فهرس مُخزَّن مؤقتاً (`getCaisseMovementsIndex`) يُبنى من جديد
  فقط عند تغيّر البيانات فعلاً — مفتاحه عدّاد نسخة البيانات
  `__omegaDataVersion` (يُزاد عند كل مسارات التعديل: دمج سحابي، `saveState`،
  حفظ/حذف عنصر) زائد أطوال الأقسام المالية. `calculateCaisseDetails` و
  `calculateAllCaisseShortages` (مع نفس تعديل `v2Stats` المؤقت للمبيعات)
  وصفوف تاريخ الإقفالات صارت عمليات بحث O(1)، مع رجوع تلقائي للمسار القديم
  عند أي خطأ. فهرس مماثل لتسديدات الكريدي والإغلاقات حسب اليوم.

### 2. مفاتيح تواريخ نصية في إحصاءات لوحة القيادة (`src/main.js`)

- استُبدلت مقارنات `new Date(...).toDateString()/getMonth()/getFullYear()`
  بمفاتيح تقويم محلية `YYYY-MM-DD` عبر `getLocalDateString` (نفس إسناد اليوم
  المعتمد أصلاً في الصندوق والإحصاءات) ومقارنات بادئات نصية للشهر/السنة، في
  حلقات الحصص والمشتركين والمبيعات وتفصيل الأصناف. التنسيقات غير القياسية
  في تفصيل الأصناف ترجع لـ`parseSafeDate` كما كانت تماماً (`isSaleInMonth`).
- دمج مسحي المصاريف وخلاصات العمال في مسح واحد لكل منهما بنفس الشروط حرفياً.
- حراس إعادة البناء: قائمة اختيار الباقة (مع الحفاظ على الاختيار الحالي)،
  قائمة الباقات، قائمة الغيابات، أيقونة العين، ومسح بيانات Mock — لا تُعاد
  إلا عند تغيّر نسخة البيانات. مصفوفة الباقات لا تُستبدل بهوية جديدة عند كل
  عرض ما لم تُحذف باقة حصص فعلاً (يبقي فهارس البحث O(1) صالحة).
- `setElemHTML` تتخطى الكتابات المتطابقة (كما تفعل `setElemText` أصلاً)، فلا
  يُعاد تفسير شظايا HTML وتخطيطها دون داعٍ عند كل عرض.

### 3. مفاتيح فرز محسوبة مرة واحدة

قوائم المبيعات والمصاريف (العرضان) ومعاملات العمال وتاريخ الصندوق تُزيّن كل
سجل بطابعه الزمني مرة واحدة ثم تفرز أرقاماً (Schwartzian transform)؛ التواريخ
غير الصالحة تُعامل كـ0 (الأخيرة تنازلياً) بدل `NaN`. فرز تاريخ الصندوق لم يعد
يُعدّل ترتيب `appState.caisseLogs` في مكانه.

### 4. تصغير HTML الإنتاج (`scripts/vite-minify-html.js`)

إضافة Vite متحفظة ومحايدة بصرياً: إزالة التعليقات (عدا `<!--!`)، وضغط مسافات
الإزاحة بين الوسوم المحتوية على سطر جديد إلى مسافة واحدة (لا صفر — حفاظاً على
العرض الحالي تماماً). محتويات `<script>` و`<style>` و`<pre>` و`<textarea>`
و`<svg>` محمية بالكامل، والنصوص والخصائص لا تُمس.

## التحقق

- `npm run lint`: ناجح.
- `npm test`: **131 اختباراً ناجحاً** — منها 3 اختبارات تكافؤ جديدة تثبت أن
  `indexCaisseMovementsByDate(day)` يساوي `buildCaisseMovements(day)` لكل يوم
  (شاملاً تسويات الاشتراكات والصندوق العام والموردين القدماء)، و8 اختبارات
  لتصغير HTML (حماية الكتل، الحياد البصري، وفحص `index.html` الحقيقي).
- `npm run test:ui` (مع jsdom): **6/6 ناجحة** — `main.js` المعدَّل يعمل داخل DOM.
- `npm run build`: ناجح؛ فحص مخرجات `dist/index.html` (العنوان، الخطوط الستة،
  سكربت الحزمة، غياب أي بقايا داخلية للتصغير).
- خادم التطوير يخدم الصفحة والوحدات المعدَّلة بنجاح (HTTP 200).

## الحدود وما لم يُفعل عمداً

- لا يوجد Chrome في بيئة القياس: لم تُشغَّل Lighthouse ولا
  `tests/startup-browser.check.mjs` في هذه الجولة. الأرقام أعلاه قياسات
  وحدة/Node حقيقية على منطق الإنتاج نفسه، لكنها ليست بديلاً عن PageSpeed
  على الرابط المنشور ببيانات فعلية — يُنصح بتشغيلهما بعد النشر.
- فصل مزيد من `main.js` إلى حزم كسولة (مزامنة Google Drive ‏~550 سطراً، مولّد
  بيانات Mock ‏~300 سطر) ما يزال عملاً لاحقاً: مكسبه عند الإقلاع (~9% من
  الحزمة الرئيسية) أصغر من مكاسب هذه الجولة أثناء التشغيل، ويتطلب اختبارات
  تفاعل متصفح أوسع قبل تنفيذه بأمان.
- لم تُختصر أي سجلات أو أرقام مالية لتحسين القياس؛ كل المجاميع تُحسب من
  البيانات الكاملة كما قبل.
