# فهرس سجل العمليات — جلب أسرع لبيانات «السجل»

## المشكلة

فتح نافذة **سجل العمليات** أو كتابة حرف واحد في مربع البحث كان يعيد بناء قائمة العرض من الصفر في كل مرة:

1. نسخ كامل مصفوفة `activityLogs`؛
2. تحويل `title` و`details` إلى أحرف صغيرة لكل سجل عند كل ضغطة مفتاح؛
3. تصفية النتائج؛
4. ترتيبها من الأحدث إلى الأقدم (`O(n log n)`).

ثم كتابة HTML ثقيل لكل الصفوف المطابقة (حتى 500 بطاقة) داخل `innerHTML`، على الخيط الرئيسي، مباشرة بعد خطوة الترتيب. أي أن كل حرف يُكتب في البحث كان يكلّف `O(n log n)` فرزًا + `O(حجم النص)` تخصيصًا لنصوص جديدة.

## الفهرس

الملف `src/activity-log-index.js` يبني فهرسًا في الذاكرة **مرة واحدة لكل تغيّر في البيانات**:

| الحقل | المحتوى | الاستخدام |
| --- | --- | --- |
| `entries` | قائمة مرتبة من الأحدث إلى الأقدم `{ id, log, ts, type, text }` | العرض والبحث |
| `byId` | `id → entry` | وصول فوري `O(1)` لسجل واحد |
| `byType` | `type → entries` مرتبة | تصفية القسم دون فرز |
| `counts` | `type → عدد` | العدادات |
| `text` | نص بحث مُطبَّع مسبقًا لكل سجل | بحث بلا تحويل متكرر |

### تطبيع نص البحث

يُطبَّق على السجل وعلى ما يكتبه المستخدم معًا، فلا يكسر أي مطابقة دقيقة:

- حذف التشكيل والتطويل (`ـ`);
- توحيد `آ أ إ ٱ → ا` و`ى → ي` و`ة → ه`;
- تحويل الأحرف اللاتينية إلى صغيرة (`Whey` = `whey`);
- ضغط المسافات. البحث بأكثر من كلمة يستخدم **AND**: كل الكلمات يجب أن توجد.

### إبطال الفهرس

`activityLogsSignature()` يحسب بصمة `العدد:هاش` فوق معرّف وتاريخ كل سجل. الفهرس يُعاد بناؤه فقط عندما تتغير البصمة أو يتغيّر مرجع المصفوفة، فيغطي كل مسارات التعديل في التطبيق: `logActivity()` (إضافة في الأعلى)، الحذف (`filter`)، الإفراغ (`= []`)، ومزامنة Firebase (مصفوفة جديدة).

## الواجهة

- صفحة أولى من **100 بطاقة** فقط (`عرض المزيد` يزيدها 100 كل نقرة، مع إظهار عدد العمليات المتبقية).
- تبقى خانة العدّاد تعرض **العدد الكامل** للنتائج المطابقة، لا عدد البطاقات المعروضة.
- تغيير نص البحث أو القسم يعيد الترقيم إلى الصفحة الأولى.
- عند عدم وجود كلمة بحث: النتيجة شريحة من القائمة المرتبة أصلًا (`O(الصفحة)` بدل `O(الصفوف)`).

## جلب بقية السجل من السحابة

مستمع Firebase لا يشترك إلا في **أحدث نافذة** (`SECTION_WINDOW_LIMITS.activityLogs = 400`)، لذلك أي سجل أقدم منها لا يوجد في الذاكرة أصلًا. لهذا أصبح زر المزيد يعمل على مرحلتين:

1. **إن كانت هناك صفحات في الذاكرة:** يكشف الصفحة التالية فورًا دون أي طلب شبكة.
2. **إن انتهت الذاكرة:** يجلب **دفعة واحدة فقط** (100 سجل) عبر `endBefore(oldestKey) + limitToLast(100)` — أي دفعة أقدم من أقدم مفتاح محمّل، وليس إعادة تنزيل العقدة كاملة.

المؤشر `window.firebaseCursors.activityLogs` يحفظ أقدم مفتاح تم تحميله و`hasMore`؛ وعندما تعود صفحة أقصر من حجم الدفعة يُغلق المؤشر لأن السجل انتهى.

كما يظهر داخل النافذة:

- ⏳ «جاري تحميل السجل من السحابة…» بدل تقديم السجلات القليلة المخزنة محليًا كأنها السجل كامل — وأي وصول جديد للسجل يُحدّث القائمة **تلقائيًا** ما دامت النافذة مفتوحة.
- ☁️ «تحميل المزيد من السجل» = دفعة أقدم واحدة من السحابة.
- «تحميل كامل السجل» = حلقة تجلب كل الصفحات الأقدم وتُظهرها تدريجيًا (بحد أقصى 1000 بطاقة معروضة، وما بعدها يبقى قابلًا للبحث).
- ✔ «تم تحميل كل السجل» عند اكتمال التاريخ.

## الكاش مع مراعاة التغيير

`src/activity-log-cache.js` يضيف ثلاث طبقات كاش، لكل واحدة قاعدة إبطال خاصة بها:

| الكاش | ما يخزّنه | متى يُبطل |
| --- | --- | --- |
| كاش البطاقات | HTML كل سجل | «بصمة» السجل: `timestamp,type,title,details,amount`. تعديل أي حقل يعيد بناء بطاقته وحدها، وباقي البطاقات تبقى كما هي |
| كاش الصفحات | نتيجة (القسم + نص البحث + حجم الصفحة) | أي تغيير في المجموعة يغيّر «بصمة البيانات» (`activityLogsSignature`) فيُسقط كل الصفحات المخزنة دفعة واحدة |
| حالة الجلب | «تم جلب كل السجل الأقدم» + أقدم مفتاح | تُحفظ في IndexedDB عبر `localCache.setKV`، ولا تُصدَّق بعد إعادة التشغيل إلا إذا كان أقدم سجل موجودًا فعلًا في الذاكرة (كاش محلي مفقود ⇒ جلب من جديد) |

بالإضافة إلى ذلك: إذا كان HTML الناتج مطابقًا لما هو معروض، لا تُلمس `innerHTML` إطلاقًا، فتبقى البطاقات المفتوحة (تفاصيل التغييرات) كما هي.

### القياس (jsdom، 500 سجل، صفحة 100 بطاقة)

| الحالة | الزمن |
| --- | ---: |
| أول عرض (بناء 100 بطاقة + كتابة DOM) | ~237 ms |
| عرض مطابق (لا كتابة DOM، كاش) | ~1.8 ms |
| بحث جديد (البطاقات من الكاش، كتابة DOM فقط) | ~7.6 ms |

## التحقق

```sh
npm test                        # يشمل tests/activity-log-index.test.js (16) و tests/activity-log-cache.test.js (8)
npm run test:activity-log-ui    # فحص jsdom لواجهة السجل: 15 فحصًا (يتطلب: npm install --no-save jsdom)
npm run lint && npm run build
```

القياس المحلي (Node 22، 500 سجل): بناء الفهرس ≈ 1 مللي ثانية، والبحث بعدها ≈ 0.03 مللي ثانية لكل ضغطة مفتاح بدل نسخ وتحويل وترتيب كامل المصفوفة. الفائدة الأكبر في المتصفح هي تقليل عدد البطاقات المعاد رسمها من 500 إلى 100 لكل تفاعل.

## ملاحظة عن فهرس Firebase

فهرس قاعدة البيانات الحقيقية موجود أصلًا في `database.rules.json`:

```json
"activityLogs": { ".indexOn": ["timestamp", "type", "dateStr"] }
```

لكن استعلامات التطبيق على السجل تستخدم `orderByKey()` (نافذة `limitToLast`) وهي مفهرسة بالمفتاح دائمًا، لذلك لا يوجد استعلام يستفيد من `.indexOn` هنا. البطء المحسوس كان في العرض والبحث على العميل، وهو ما يعالجه هذا الفهرس.
